# Production: обновление и диагностика

MCP-прокси работает в production на отдельной Linux-ВМ в Docker. Репозиторий на ВМ склонирован из `origin` (ветка `main`), обновление — `git pull` и пересборка контейнера. Этот файл — регламент для человека и для AI-агента.

> Это **боевой** сервер: им пользуются сотрудники. Любое изменение (pull, пересборка, перезапуск) выполняйте только с явного согласия владельца. Чтение логов и состояния — безопасно.

## Переменные доступа (`.env` на локальной машине)

Файл `.env` в корне репозитория не коммитится (см. `.gitignore`). Помимо рабочих настроек прокси в нём лежат четыре переменные для доступа к production-ВМ. Прокси их не читает — они нужны только для отладки и деплоя.

| Переменная | Значение |
| --- | --- |
| `MCP_DEPLOY_SERVER` | IP или имя production-ВМ |
| `MCP_DEPLOY_USERNAME` | пользователь SSH (состоит в группе `docker`, `sudo` не нужен) |
| `MCP_DEPLOY_PASSWORD` | пароль SSH |
| `MCP_DEPLOY_DIR` | каталог клона репозитория на ВМ (`~/itmcp`) |

Пароль нельзя выводить в консоль, в логи и в чат.

## Подключение с Windows (Git Bash)

`sshpass` на машине разработчика нет, зато установлен PuTTY, поэтому используется `plink`. Параметры читаются из `.env` в переменные оболочки, пароль маскируется в выводе:

```bash
set -a; . <(grep -E '^MCP_DEPLOY_' .env | tr -d '\r'); set +a
PL="plink -batch -ssh -pw $MCP_DEPLOY_PASSWORD $MCP_DEPLOY_USERNAME@$MCP_DEPLOY_SERVER"
$PL 'cd ~/itmcp && git log --oneline -3' 2>&1 | sed "s/$MCP_DEPLOY_PASSWORD/***/g"
```

Замечания:

- `-batch` отключает интерактивные запросы. При первом подключении к новому хосту plink откажется работать, пока ключ хоста не будет принят: один раз выполните `plink -ssh user@host exit` вручную и ответьте `y`.
- `~` в `MCP_DEPLOY_DIR` раскрывается на стороне ВМ, поэтому команду передавайте в одинарных кавычках.
- Если вывод нужен без сжатия RTK, запускайте через `rtk bypass`.

## Что где лежит на ВМ

| Что | Значение |
| --- | --- |
| Каталог проекта | `~/itmcp` (`MCP_DEPLOY_DIR`) |
| Remote / ветка | `origin` = `https://github.com/Diversus23/itmcp.git`, ветка `main` |
| Конфигурация | `~/itmcp/.env` на ВМ — **отдельный** файл, не совпадает с локальным |
| Контейнер | `mcp-proxy` (образ `itmcp-mcp-proxy`), порт `8000` |
| Данные | именованный том `itmcp_mcp-data` → `/app/data` (снапшот OAuth2-токенов) |
| Публичный адрес | `MCP_PUBLIC_URL` из `.env` на ВМ, TLS и reverse proxy — снаружи контейнера |

Том `itmcp_mcp-data` сохраняет авторизацию клиентов при пересоздании контейнера. Не удаляйте его (`docker compose down -v` запрещено).

## Обновление production

1. Убедитесь, что нужные изменения уже в `origin/main`: локально `git push`.
2. Проверьте состояние на ВМ:

   ```bash
   $PL 'cd ~/itmcp && git status -s && git log --oneline -1 && docker ps --format "{{.Names}} {{.Status}}"'
   ```

   Если `git status` показывает локальные правки на ВМ — остановитесь и спросите владельца.
3. Подтяните изменения и пересоберите контейнер:

   ```bash
   $PL 'cd ~/itmcp && git pull --ff-only && docker compose up -d --build'
   ```

   `up -d --build` пересобирает образ и пересоздаёт контейнер, не затрагивая том. Простой — несколько секунд. Флаг `--no-cache` нужен только если не подхватились изменения зависимостей.
4. Проверьте результат:

   ```bash
   $PL 'sleep 10; docker ps --format "{{.Names}} {{.Status}}"; curl -s localhost:8000/health; echo; docker logs --tail 30 mcp-proxy'
   ```

   В ответе `/health` ожидается `"status":"healthy"` и новая `version`. Статус контейнера должен перейти в `healthy` (HEALTHCHECK срабатывает раз в 30 с).

### Изменение `.env` на ВМ

`.env` читается только при создании контейнера, поэтому после правки нужен `docker compose up -d` (просто `restart` переменные не перечитает). Не выводите файл целиком — маскируйте секреты:

```bash
$PL 'cd ~/itmcp && grep -vE "^\s*#|^\s*$" .env | sed -E "s/^([A-Z0-9_]*(PASSWORD|SECRET|TOKEN)[A-Z0-9_]*)=.*/\1=***/"'
```

### Откат

```bash
$PL 'cd ~/itmcp && git log --oneline -5'        # найти предыдущий коммит
$PL 'cd ~/itmcp && git checkout <sha> && docker compose up -d --build'
```

После отката вернитесь на `main` (`git checkout main`), когда исправление будет готово.

## Диагностика

Логи (уровень по умолчанию `INFO`, для подробностей поставьте `MCP_LOG_LEVEL=DEBUG` в `.env` на ВМ и пересоздайте контейнер):

```bash
$PL 'docker logs --tail 100 mcp-proxy'
$PL 'docker logs --since 1h mcp-proxy 2>&1 | grep -E "ERROR|WARNING"'
```

Состояние самого прокси: `curl -s localhost:8000/health` на ВМ. Поле `onec_connection` всегда `not_checked`: `/health` прокси не обращается к 1С.

### Ошибка `1C service unavailable: HTTP <код>` / страница «Ошибка подключения к 1С»

Прокси при создании сессии и при авторизации вызывает `GET <MCP_ONEC_URL>/hs/<MCP_ONEC_SERVICE_ROOT>/health` в 1С. Любой статус, кроме 2xx, превращается в эту ошибку (401/403 — отдельно, как «неверный логин или пароль»). Значит, `HTTP 500` приходит именно от веб-сервера 1С, а не от прокси. Проверьте ответ 1С прямо с ВМ, минуя прокси:

```bash
$PL 'curl -s -m 15 -i http://<адрес 1С>/<публикация>/hs/mcp/health | head -20'
```

Начиная с версии 1.2.5 прокси сам читает тело ответа 1С и пишет причину в текст ошибки: `HTTP 500: IsapiModule / 1C Web-service Extension / 0x80004005` (модуль / обработчик / код ошибки IIS), а следом — подсказку, что проверить (например, «Вероятно, информационную базу 1С необходимо опубликовать на веб-сервере»). Сводка и подсказка видны в ответе MCP, на странице входа и в ответах инструментов. Полные подробности (URL, физический путь на сервере IIS) пишутся только в лог контейнера строкой `1С ответила HTTP …`. Сетевые сбои (отказ в соединении, DNS, таймаут) приходят как `Нет связи с 1С (ECONNREFUSED)` тоже с подсказкой; адрес сервера — только в лог (`Нет связи с 1С […]`).

- `401` без авторизации — это норма: публикация жива, сервис требует логин.
- `500` с HTML от IIS — сломана веб-публикация. В теле страницы смотрите блок «Подробные сведения об ошибке»: модуль, обработчик, код ошибки, физический путь.
- Если запрос на корень публикации (`/<публикация>/`) тоже даёт 500, проблема не в HTTP-сервисе MCP, а в публикации базы целиком: расширение веб-сервера 1С (`wsisapi.dll`), `default.vrd`, строка соединения, доступность сервера 1С.
